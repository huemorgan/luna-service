# Luna suggestion — Vault virtual keys (gateway connections as a key type)

**For the Luna team. Proposal only — no code here.** Companion to luna-service plan
026 / 026.1. This asks for a vault-plugin feature so platform-provided (gateway) keys
appear in the **Key Vault** next to the user's own keys.

## The ask in one line

Make the vault model **two key types**: **real** (BYOK, secret stored) and
**Luna-Service-Provisioned** (virtual — no secret on the machine; routes through the
hosting gateway). Surface both in the Key Vault tab; resolve both through one method.

## Why

Hosted Luna brokers API keys through a central gateway (the machine holds only a device
token; the real key stays server-side and usage is metered/billed). Today connector
plugins either need a user-pasted vault secret or read a hidden env var. We want the
user to **see** the keys we provide, the agent to **suggest/connect** more, and plugins
to consume either source uniformly — all inside the vault, which is already the
credentials surface (`SettingsTab "Key Vault"`).

## Design (please critique)

### 1. A key *type*, not a new table
- Add a `source`/`type` discriminator to credentials: `real` vs
  `luna_service_provisioned` (virtual).
- **Do not add a local `gateway` table.** Virtual keys are a **live projection** from
  the host control plane (endpoint below), unioned into the Key Vault list at
  render/resolve time, with a short in-process cache. The only machine-local state is
  `LUNA_GATEWAY_URL` (already present) + the device token (`LUNA_GATEWAY_TOKEN`).
- Real keys keep living in `vault_credentials` unchanged.

### 2. Vault becomes a connection registry: `connect()`
Add to the `VaultProvider` contract (and implement in `PostgresVaultProvider`):

```
async def connect(self, slug: str, *, upstream_default: str, auth: AuthSpec) -> Connection | None
```

`Connection` (new dataclass in `luna/providers`, re-exported from `luna_sdk`):

```
Connection(base_url: str, secret: str, header: str, scheme: str | None,
           source: Literal["real","virtual"], billed: bool)
```

Resolution precedence:
1. **Real BYOK** row for `slug` → `base_url=upstream_default`, `secret=<stored>`,
   `billed=False`.
2. **Virtual** (host says this agent is provisioned for `slug` and a pool key exists) →
   `base_url={LUNA_GATEWAY_URL}/<slug>`, `secret=<device token>`, `billed=True`.
3. else `None` (not connected).

A plugin just does: `conn = await ctx.vault.connect("monday", ...)` then sends
`conn.secret` in `conn.header` to `conn.base_url`. It never knows or cares which type it
got. (`resolve_credential()` stays for plain secret lookups; `connect()` is additive.)

### 3. Host discovery endpoint (provided by luna-service)
`GET {LUNA_GATEWAY_URL%/proxy}/api/agent/gateway/services`, authed by the device token,
returns this agent's `provisioned` + `available` services (slug, display_name, purpose,
proxy_url, auth header/scheme, has_key, status) — **no secrets**. The vault projects
virtual keys from this. (Spec lives in luna-service 026.1.)

### 4. Key Vault tab
- List real + virtual together; virtual entries badged "Provided by Luna Cloud", **no
  reveal button**, optional usage/last-used.
- A section for `available` services (from discovery) so the user — or the agent — can
  connect more with one click.

### 5. Agent self-service tools + skill (in plugin-vault) — merged from old plan 027
The agent uses the **same** discovery inventory + `connect()` to solve key problems on
its own. One place, not a separate `plugin-gateway`.

- `list_available_gateway_keys()` → the discovery inventory ("what keys we offer" +
  what this agent already has).
- `connect_gateway_key(slug)` → ask the host to provision the binding; the virtual key
  then appears in the vault and resolves.
- Escape hatch for ad-hoc / user-written code: call the proxy directly with the device
  token (billed to the workspace).
- Auto-connect loop: a plugin that loads inactive → find its binding → connect if a key
  exists → else honest "no key, here's BYOK", no looping.
- **User-developed plugins** get the same deal via `ctx.vault.connect(slug)`; broad
  access is safe because every call is metered to the paying workspace.
- A `SkillDef`: "external keys are brokered through the gateway and billed to this
  workspace; check `list_credentials` / `list_available_gateway_keys` before asking the
  user for a key; connect instead of begging; never fabricate a key we don't pool."

## Boundaries / back-compat
- Purely additive: `resolve_credential` and existing rows untouched; old cores that lack
  `connect()` degrade (consumers use `getattr(ctx.vault, "connect", None)`).
- Extra non-secret params (e.g. funnelfighters `org_id`, monday board ids) stay normal
  vault/config — `connect()` only brokers the secret + endpoint.
- Plugins migrate one at a time to `ctx.vault.connect(slug)` (luna-plugins side);
  `plugin-connectors` is already proxy-shaped and is the reference.

## Open questions for you — DECIDED (Luna side, 008.991)
1. **`connect()` lives on `VaultProvider`** (concrete default = real-BYOK only;
   `plugin-vault` overrides `connect_virtual()` for the gateway branch). The vault is the
   credentials owner + UI surface, so no sibling capability. `InMemory`/HashiCorp/AWS
   backends inherit working real connections for free.
2. **Short poll: 60s in-process TTL cache, busted on `connect_gateway_key`.** No events in
   v1; a 60s window is short enough and connect invalidates immediately.
3. **Host-only enable/disable.** No local authoritative state — virtual keys are a live
   projection from discovery (no table, no `source` column). Local override = the user adds
   a real BYOK key with the matching name (real > virtual); the external row then shows an
   *"Overridden by your private key"* note.

### What Luna shipped (this half, 008.991)
- `AuthSpec` + `Connection` (+ `Connection.apply`, header AND query auth) in
  `luna/providers/vault.py`, re-exported from `luna_sdk`.
- `VaultProvider.connect()` (concrete, real→virtual→None) + `connect_virtual()` (default
  `None`); `ScopedVault` gates the real branch and leaves virtual open.
- `plugin-vault`: gateway discovery client (reads `LUNA_GATEWAY_URL`/`LUNA_GATEWAY_TOKEN`
  live, 60s cache), `connect_virtual()` projection, device-token sanitizer registration,
  the unioned Key Vault view + UI (gateway block / your / external / available / collapsed
  add), and agent tools `list_available_gateway_keys` / `connect_gateway_key` + a
  `gateway-keys` skill.
- `EnvConfig.gateway_url` / `gateway_token` so `ctx.get_env("LUNA_GATEWAY_*")` resolves.

### What luna-service still owes (the control-plane half)
- `GET {base}/api/agent/gateway/services` (device-token auth, secrets-free) returning
  `[{slug, display_name, purpose, proxy_url, auth_header, auth_scheme, provisioned,
  has_key, status}]`. Optional `auth_location:"query"` + `auth_query_param` for query-keyed
  services (e.g. GIPHY) — Luna already handles both.
- A bind endpoint for `connect_gateway_key` (Luna POSTs `{base}/api/agent/gateway/connect`
  `{slug}`; it degrades to a cache-bust + re-discovery if absent, so an already-pooled key
  still resolves).
